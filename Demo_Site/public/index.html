Addressing Concern 1: The Meaning of MCP Prompts

Reconciling MCP 2.0 Reusable Templates with OData Enterprise Semantic Retrieval

🌐 Official MCP 2.0 Specification ↗
⚠️ "The meaning of MCP prompts was unclear. The proposal described prompts as a search index, but the MCP specification presents them more like reusable templates."
MCP Specification View 📄 Spec: 2026-07-28 ↗

Reusable Parameterized Templates

In the official Model Context Protocol (MCP 2.0 / 2026-07-28), prompts are designed as user-controlled slash-command-style templates:

  • Interactive workflows: Invoked when a user selects a template (e.g., /whom_olga_reports_to) with client-specific optional automation via prompts/get.
  • Message Generators: Accept arguments (e.g., userName="Olga") and expand into a sequence of structured prompt messages (role: "user", content: { text: "..." }).
  • OData query steps: Container prompts express workflows using standard OData v4.01 queries against the service schema.
🔗 MCP Specification Link: https://modelcontextprotocol.io/specification/2026-07-28 (also see Concepts: Prompts)
OData TC / Enterprise View

Semantic Retrieval Index (Catalog)

For large enterprise APIs like Microsoft Graph (with 1,000+ endpoints), exposing individual tools saturates LLM context windows:

  • Context Window Constraint: Large tool catalogs can consume context; this demo does not establish a universal tool-count limit.
  • Work IQ & Graph Copilot Pattern: Instead of 1,000 tools, services use a catalog of curated natural-language prompt workflows to index API calls.
  • Search-then-Query: The agent matches user utterances (such as "Who is Olga's manager?") against prompt descriptions and OData query templates to select the appropriate tool or API request.

Separate contracts: prompt templates and discovery

MCP discovery lists prompt names and arguments; prompts/get renders a selected template. Core MCP does not prescribe automatic intent routing, argument extraction, or fetching every prompt. Those are client/harness decisions.

Server A declares container-level Agent.Prompts authored with OData v4.01 query steps; Server B is a baseline CSDL without prompt annotations.

Standard OData EntitySet and Singleton declarations are projected to MCP tools and resources first. A container prompt can then compose both users and groups through multi-step OData queries. Reporting peers, group membership and group ownership are different facts: none of these combined workflows can be assigned to a single entity set.

The CLI benchmark fetches the actual catalogs first, then lets the model route each query and call the assigned MCP. This is where free-text argument extraction is evaluated.

Discovery, Determinism & Multi-Request Execution

  • prompts/list vs prompts/get: prompts/list returns only prompt signatures and required arguments; prompts/get returns rendered messages after argument extraction.
  • Free-Text Utterance vs User Selection: Clients/LLMs map free-text questions to discovered prompts/tools, extract arguments, and reject out-of-domain queries (such as weather) with zero tool calls.
  • Deterministic Projection & Multi-Turn Disambiguation: CSDL-to-MCP conversion uses deterministic C# code (no AI rewriting or non-standard prompt_template fields). Ambiguous names (multiple "Olga" matches) require find_user with Graph-valid $filter=startswith(...) (not unsupported contains(...)) before calling user_profile or resources/read.

Key Conclusions: Why MCP Queries Fail Without CSDL @Agent.Prompts

Baseline B Failure Rate: 44.3% (27/61 failed) vs Variant A: 8.2% (5/61 failed)

Without container-level @Agent.Prompts in CSDL, the agent only sees raw tool and resource schemas, resulting in five recurring failure patterns across the 61-query benchmark:

1. Ambiguous Identity Resolution Queries #1–#3, #11–#15, #18, #22, #25, #28

First-Name Disambiguation Failures

Without prompt defaults (userName="Olga", managerName="Alex Wilbur"), calling find_user("Olga") against a large directory returns 20 matches and aborts with needs_clarification instead of resolving the target profile.

2. Missing Workflow Defaults Queries #21, #42

Missing Default Parameters

Canonical workflow utterances such as "Direct reports of a manager" and "User quick lookup" fail with 0 MCP tool calls because raw tool schemas lack the prompt-level default parameters needed to execute the lookup.

3. Unrecognized OData Filters Queries #31, #34–#38

False out_of_scope on Attribute Filters

Without search_users_by_dept_title illustrating GET users?$filter=department eq '...' and startswith(jobTitle,'...'), the model assumes find_user only searches display names/UPNs and falsely rejects department and job-title queries as out_of_scope.

4. Entity-Set Confusion Queries #32, #33

Entity-Set Misrouting (groups vs users)

Department-scoped user queries such as "Find architects in Identity" and "Find all Principal Architects in Architecture & Standards" misroute to find_group("Identity") instead of querying the users entity set.

5. Multi-Resource Orchestration Queries #59–#61 (0/3 vs 3/3)

Incomplete Cross-Resource Joins

On composed queries requiring both organizational reporting lines (users) and group membership/ownership (groups), Baseline B stops after a single tool call, whereas @Agent.Prompts guides the agent to read and join both users://{userId} and groups://{groupId}.

Deterministic Engine #2

2. Deterministic CSDL Projection

No LLM performs the conversion. The same annotated schema always produces the exact same MCP contract.

  • Standard OData EntitySet and Singleton declarations → tools/list schemas, resources/list URIs/templates, and operation dispatch (no tool or resource annotations in CSDL).
  • Container Agent.Prompts → prompts/list discovery and parameter-substituted prompts/get OData query instructions.
  • Canonical XML is validated via Microsoft.OData.Edm; CSDL JSON ($Version: "4.01") is projected from the same XML.

6. Execution and Non-Deterministic Parts

This is not a compiler for arbitrary CSDL or arbitrary REST APIs.
