Addressing Concern 1: The Meaning of MCP Prompts

            
Reconciling MCP 2.0 Reusable Templates with OData Enterprise Semantic Retrieval

          

          

            
              🌐 Official MCP 2.0 Specification ↗
            
          

        

        

          ⚠️
          "The meaning of MCP prompts was unclear. The proposal described prompts as a search index, but the MCP specification presents them more like reusable templates."
        

      


      

        
        

          

            

              

                MCP Specification View
                
                  📄 Spec: 2026-07-28 ↗
                
              

              
Reusable Parameterized Templates

            

            
In the official Model Context Protocol (MCP 2.0 / 2026-07-28), prompts are designed as user-controlled slash-command-style templates:

            
    
              
  • Interactive workflows: Invoked when a user selects a template (e.g., /whom_olga_reports_to) with client-specific optional automation via prompts/get.
    • 
              
  • Message Generators: Accept arguments (e.g., userName="Olga") and expand into a sequence of structured prompt messages (role: "user", content: { text: "..." }).
    • 
              
  • OData query steps: Container prompts express workflows using standard OData v4.01 queries against the service schema.
    • 
            

            

              🔗 MCP Specification Link: https://modelcontextprotocol.io/specification/2026-07-28 (also see Concepts: Prompts)
            

          


          

            

              OData TC / Enterprise View
              
Semantic Retrieval Index (Catalog)

            

            
For large enterprise APIs like Microsoft Graph (with 1,000+ endpoints), exposing individual tools saturates LLM context windows:

            
    
              
  • Context Window Constraint: Large tool catalogs can consume context; this demo does not establish a universal tool-count limit.
    • 
              
  • Work IQ & Graph Copilot Pattern: Instead of 1,000 tools, services use a catalog of curated natural-language prompt workflows to index API calls.
    • 
              
  • Search-then-Query: The agent matches user utterances (such as "Who is Olga's manager?") against prompt descriptions and OData query templates to select the appropriate tool or API request.
    • 
            

          

        



        

          
Separate contracts: prompt templates and discovery

          
MCP discovery lists prompt names and arguments; prompts/get renders a selected
            template. Core MCP does not prescribe automatic intent routing, argument extraction, or
            fetching every prompt. Those are client/harness decisions.

          
Server A declares container-level Agent.Prompts authored with OData v4.01 query steps;
            Server B is a baseline CSDL without prompt annotations.

          
Standard OData EntitySet and Singleton declarations are projected to MCP tools and resources first.
            A container prompt can then compose both users and groups through multi-step OData queries.
            Reporting peers, group membership and group ownership are different facts: none of these
            combined workflows can be assigned to a single entity set.

          

          
The CLI benchmark fetches the actual catalogs first, then lets the model route each query
            and call the assigned MCP. This is where free-text argument extraction is evaluated.

          OData TC Review Concerns (transcript-2026-10-28.md)
          
Discovery, Determinism & Multi-Request Execution

          
    
            
  • prompts/list vs prompts/get: prompts/list returns only prompt signatures and required arguments; prompts/get returns rendered messages after argument extraction.
    • 
            
  • Free-Text Utterance vs User Selection: Clients/LLMs map free-text questions to discovered prompts/tools, extract arguments, and reject out-of-domain queries (such as weather) with zero tool calls.
    • 
            
  • Deterministic Projection & Multi-Turn Disambiguation: CSDL-to-MCP conversion uses deterministic C# code (no AI rewriting or non-standard prompt_template fields). Ambiguous names (multiple "Olga" matches) require find_user with Graph-valid $filter=startswith(...) (not unsupported contains(...)) before calling user_profile or resources/read.

Key Conclusions: Why MCP Queries Fail Without CSDL @Agent.Prompts

            Baseline B Failure Rate: 44.3% (27/61 failed) vs Variant A: 8.2% (5/61 failed)
          

          

            Without container-level @Agent.Prompts in CSDL, the agent only sees raw tool and resource schemas, resulting in five recurring failure patterns across the 61-query benchmark:
          

          

            

              

                1. Ambiguous Identity Resolution
                Queries #1–#3, #11–#15, #18, #22, #25, #28
              

              
First-Name Disambiguation Failures

              
Without prompt defaults (userName="Olga", managerName="Vojtech Vondra"), calling find_user("Olga") against a large directory returns 20 matches and aborts with needs_clarification instead of resolving the target profile.

            


            

              

                2. Missing Workflow Defaults
                Queries #21, #42
              

              
Missing Default Parameters

              
Canonical workflow utterances such as "Direct reports of a manager" and "User quick lookup" fail with 0 MCP tool calls because raw tool schemas lack the prompt-level default parameters needed to execute the lookup.

            


            

              

                3. Unrecognized OData Filters
                Queries #31, #34–#38
              

              
False out_of_scope on Attribute Filters

              
Without search_users_by_dept_title illustrating GET users?$filter=department eq '...' and startswith(jobTitle,'...'), the model assumes find_user only searches display names/UPNs and falsely rejects department and job-title queries as out_of_scope.

            


            

              

                4. Entity-Set Confusion
                Queries #32, #33
              

              
Entity-Set Misrouting (groups vs users)

              
Department-scoped user queries such as "Find architects in Identity" and "Find all Principal Architects in Architecture & Standards" misroute to find_group("Identity") instead of querying the users entity set.

            


            

              

                5. Multi-Resource Orchestration
                Queries #59–#61 (0/3 vs 3/3)
              

              
Incomplete Cross-Resource Joins

              
On composed queries requiring both organizational reporting lines (users) and group membership/ownership (groups), Baseline B stops after a single tool call, whereas @Agent.Prompts guides the agent to read and join both users://{userId} and groups://{groupId}.

            Phase 1 • Demonstrated in this POC
            @Agent.Prompts
          

          
First CSDL Improvement: Container Prompt Annotations

          
This POC establishes the first CSDL improvement for AI readiness: enriching standard OData metadata (EntitySet, Singleton, NavigationPropertyBinding) with container-level @Agent.Prompts that express multi-step OData v4.01 queries. Compared against a baseline CSDL without prompts, this single improvement raised verified agent routing accuracy from 55.7% to 91.8% (+36.1 pp).

        

        
→

        

          

            Phase 2 • Next Proposed Improvement
            Additional Example Annotations
          

          
Next Evolution: Example Annotations to Simplify AI Agent Consumption

          
Building on @Agent.Prompts, the next improvement to consider is introducing additional example annotations on CSDL resources/entity sets. Curated utterance-to-OData example annotations will further simplify CSDL consumption by AI agents, enabling lightweight semantic indexing and precise filter construction across massive enterprise schemas without saturating context windows.

6. Execution and Non-Deterministic Parts

          
          

            
This is not a compiler for arbitrary CSDL or arbitrary REST APIs.

            
    
              
  • C# Handler Registry: Supported Microsoft Graph operations remain implemented in C#; schema bindings select those handlers.

  • Live vs Fallback Data: Authentication uses Azure CLI against live Graph v1.0 with deterministic fallback when offline.

Transformation 1: CSDL EntitySet / Singleton → OData Read Bindings → MCP Tools + Resources / Resource Templates

            54 Read Tools + 11 Concrete Resources + 10 Resource Templates
          

          

            CSDL EntitySet / Singleton (+ NavigationProperty)
            →
            StaticModelGenerator.CollectBindings()
            →
            ODataRequestBinding + ResourceBinding
            →
            GeneratedModel.McpTools / McpResources / McpResourceTemplates
            →
            CsdlMcpProjection.ListTools() / ListResources() / ListResourceTemplates()
          

          

            
              

                Stage
                C# Class & Method
                Input Artifact / Type
                Emitted / Returned C# Type
                Transformation Rule
              

            
            
              

                1. CSDL Parse
                StaticModelGenerator.CollectBindings(IEdmModel)
                IEdmEntitySet, IEdmSingleton, IEdmNavigationProperty
                List<BindingSpec> & List<ResourceSpec>
                Emits list_{set} (collection GET), get_{set} (keyed entity GET), get_{singleton} (singleton GET), and get_{source}_{nav} (navigation GET), all with OperationKind.Read and QueryOptions = true.
              

              

                2. Read Binding & Schema
                StaticModelGenerator.BuildSchemaJson() & WriteBinding()
                BindingSpec (Key parameters + OData system query options)
                ODataRequestBinding + ParameterBinding[] in GeneratedModel.RequestBindings
                Generates JSON Schema (filter, select, expand, orderby, top, skip, count, search + key_{name}) and pre-parses Tool.InputSchema into GeneratedModel.McpTools.
              

              

                3. Resource & URI Template
                StaticModelGenerator.UriPattern(uriTemplate) & WriteResource()
                {set}://all, {set}://{{key}}, {singleton}://default
                ResourceBinding (with compiled Regex MatchPattern) in GeneratedModel.Resources
                Links each resource URI directly to its shared ODataRequestBinding (`RequestBindings[idx]`) and emits GeneratedModel.McpResources (concrete) and GeneratedModel.McpResourceTemplates (templated).
              

              

                4. MCP Discovery
                CsdlMcpProjection.ListTools()
CsdlMcpProjection.ListResources()
CsdlMcpProjection.ListResourceTemplates()		
                MCP tools/list, resources/list, resources/templates/list
                ListToolsResult, ListResourcesResult, ListResourceTemplatesResult
                Serves pre-built protocol objects in O(1) memory without runtime XML parsing or schema generation.

Transformation 2: CSDL Function / Action → Typed Operation Binding + Generated JSON Schema → MCP Tool

            5 Bound Operations (3 Functions + 2 Actions)
          

          

            CSDL <Function> / <Action>
            →
            StaticModelGenerator.DescribeType() + BuildSchemaJson()
            →
            ODataRequestBinding (Function | Action) + StaticTypeDescriptor
            →
            GeneratedModel.McpTools + EdmJsonSchema.Validate()
          

          

            
              

                Stage
                C# Class & Method
                Input Artifact / Type
                Emitted / Returned C# Type
                Transformation Rule
              

            
            
              

                1. Operation Binding
                StaticModelGenerator.CollectBindings(IEdmModel)
                Bound IEdmFunction / IEdmAction + binding IEdmEntitySet / IEdmSingleton
                BindingSpec ({set}_{ns}_{op})
                Combines binding entity keys (IsKey = true) with non-binding IEdmOperationParameters (IsKey = false); sets OperationKind.Function or OperationKind.Action.
              

              

                2. EDM Type & Facet Mapping
                StaticModelGenerator.DescribeType(IEdmTypeReference)
                IEdmPrimitiveType, IEdmEnumType, IEdmComplexType, IEdmCollectionType
                StaticTypeDescriptor + StaticProperty[]
                Maps EDM types to StaticTypeKind (String, Boolean, Integer, Number, Guid, Date, DateTimeOffset, Duration, Enum, Object, Array) with integer bounds and enum members.
              

              

                3. JSON Schema Emission
                StaticModelGenerator.BuildSchemaJson() & WriteTypeSchema()
                IReadOnlyList<ParamSpec> + QueryOptions flag
                Draft 2020-12 InputSchemaJson string + Tool.InputSchema
                Composable collection-returning functions include OData read query options; actions set QueryOptions = false and require body parameters in inputSchema.required.
              

              

                4. Runtime Enforcement
                EdmJsonSchema.Validate() & EdmJsonSchema.Literal()
                StaticTypeDescriptor + JsonElement argument
                Validated OData literal (@param='...') or JSON POST body
                Enforces nullability, integer ranges, enum sets, ISO-8601 dates, and complex object properties before executing the function or action.

// 2. Attached to tools/call & resources/read output in Csdl/CsdlMcpProjection.cs
private static string SerializeResponse(ODataRequestBinding binding, ODataExecution execution)
{
    var examples = CsdlProvider.GetExamplesFor(binding).Select(example => new {
        targetKind = example.TargetKind, targetName = example.TargetName, entitySet = example.EntitySet,
        utterance = example.Utterance, request = example.Request, description = example.Description
    });
    return JsonSerializer.Serialize(new {
        method = execution.Method.Method, odataQuery = execution.ODataQuery,
        entitySet = binding.EntitySet, data = execution.Data, examples
    }, new JsonSerializerOptions { WriteIndented = true });
}

          

        


        
        

          

            
Transformation 5: MCP tools/call or resources/read → Generated OData Path/Body → In-Process OData Service Execution → JSON Response with Matching Examples

            End-to-End Runtime Request Execution Pipeline
          

          

            HTTP POST / → Program.cs (app.MapMcp())
            →
            CsdlMcpProjection.CallToolAsync() / ReadResourceAsync()
            →
            ExecuteAsync() + EdmJsonSchema
            →
            ODataClientService.SendAsync()
            →
            GeneratedGraphExecutor.ExecuteAsync()
            →
            GraphClientService
            →
            SerializeResponse() → HTTP 200 JSON-RPC
          

          

            
              

                Runtime Step
                C# Class & Method
                Input
                Output
                Execution Responsibility
              

            
            
              

                1. HTTP Transport & Route Entry
                Program.cs: app.MapMcp() →
WithCallToolHandler / WithReadResourceHandler		
                HTTP POST / with JSON-RPC 2.0 request body
                RequestContext<CallToolRequestParams> or RequestContext<ReadResourceRequestParams>
                ASP.NET Core stateless Streamable HTTP endpoint (ModelContextProtocol.AspNetCore) parses the JSON-RPC envelope, resolves CsdlMcpProjection from DI, and dispatches by MCP method.
              

              

                2. MCP Handler Entry
                CsdlMcpProjection.CallToolAsync()
CsdlMcpProjection.ReadResourceAsync()		
                CallToolRequestParams or ReadResourceRequestParams
                Resolved ODataRequestBinding + IDictionary<string, JsonElement>
                Looks up tool by name in CsdlProvider.GetRequestBindings() or matches URI via ResourceBinding.MatchPattern + EdmJsonSchema.ParseKey().
              

              

                3. OData Path & Body Construction
                CsdlMcpProjection.ExecuteAsync() + EdmJsonSchema.Validate() / Literal()
                ODataRequestBinding + runtime arguments
                HttpMethod (GET/POST), OData path, optional JSON body
                Validates arguments against StaticTypeDescriptor, formats key predicates (users('...')), function aliases ((@q=@q)&@q='...'), and query options (?$filter=...&$select=...), or serializes action POST body.
              

              

                4. In-Process OData Service
                ODataClientService.SendAsync()
                ODataRequestBinding, arguments, method, path, body
                JsonElement payload + recorded ODataTrace
                Measures execution duration via Stopwatch, calls GeneratedGraphExecutor.ExecuteAsync(), unwraps envelope.data, and appends an ODataTrace record.
              

              

                5. Workload Dispatch & Graph Call
                GeneratedGraphExecutor.ExecuteAsync() → GraphClientService
                binding.ExecutionKind + decoded OData path
                Live Microsoft Graph v1.0 JSON or typed GraphModels DTO + GraphTraceRecord
                Dispatches GraphExecutionKind.Direct to GraphClientService.ExecuteODataQueryAsync(decodedPath) (live Graph v1.0 with Azure CLI token or ExecuteMockODataQueryAsync fallback) and specialized kinds to workload helpers.
              

              

                6. Grounded MCP Result & HTTP Response
                CsdlMcpProjection.SerializeResponse() → app.MapMcp()
                ODataRequestBinding + ODataExecution
                CallToolResult / ReadResourceResult → HTTP 200 OK JSON-RPC response
                Serializes { method, odataQuery, entitySet, data, examples } into the MCP content block and writes the HTTP 200 JSON-RPC response.
